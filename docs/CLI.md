# `orch` (Go) — implemented subcommands

A short, living page: what the Go binary actually does today, updated in the
same PR that wires a new subcommand. The trilingual manual
(`docs/MANUAL.{en,es,pt}.md`) describes the **Python** `orch` and stays valid
as the flag *contract* — a subcommand listed here should accept the same
flags Python does unless a difference is called out.

**Status by phase** (see the "Orch en Go" migration plan):

- **G1.5 — landed**: `status`, `tasks`, `events`, `logs`.
- **G4.4 — landed**: `init` (batch + wizard).
- **G3.6 — landed**: `task set`, `task-status`, `reset`. `stop` was split out
  to **G3.3** (it needs the engine's run tracking, not `Backend.Transition`
  — see `docs/brainstorm/go-migration-notes.md`).
- **G1.6 — landed**: `validate`, `graph`, `router validate`, `router
  add-missing`, `config show`, `atomize`.
- **G4.6 — landed**: `migrate` (narrower than Python — see its table row).
- **G8.5 — landed**: `dashboard --portfolio` (new in Go — one process, N
  projects; see [`DASHBOARD-PROFILES.md`](DASHBOARD-PROFILES.md)).
- **G6.7 — landed**: `notify test`, `notify digest`. The `sprint_done` event
  (F4.7) lands with them: `orch run` writes one run-level row when its queue
  empties, carrying the task counts it finished with — see the `run` row.
- **G6.4 — landed**: `mcp` (new in Go — Python has no MCP server; see
  [`MCP.md`](MCP.md)). **G6.6** then made `run`'s dispatch prompt offer those
  tools first, with the scripts as the fallback.
- **G6.5 — landed**: `install-skills` (wider than Python — see its table
  row). Six skills are embedded: `orch`, the operating manual, and the
  planning pipeline `orch-plan` → `orch-prd` → `orch-arch` → `orch-spec` →
  `orch-tasks` (idea → `docs/prd/` → `docs/arch/` → `specs/` →
  `orch atomize --apply`). The five pipeline skills were written for G6.5 —
  before it they existed only as names in the docs. Each one is checked
  against this binary in `internal/cli/skills_contract_test.go`: every
  `orch …` invocation must resolve to a real command and flag, and
  `orch-spec`'s example spec must go through the real atomize parser with no
  warnings.
- **G4.5 — landed**: `doctor` (narrower than Python — see its table row).
  `internal/doctor`'s checks (the package) landed earlier; this is the
  `orch doctor` command surface on top of them, wired separately.
- **G5.2 / G5.4 / G5.6 — landed**: `dashboard` (the HTTP server, the nine read
  endpoints the SPA consumes, the two tunnel routes and the live event stream).
- **G6.8 — landed**: `explain` (new in Go; shares `internal/explain.Gather`
  with the MCP server's `orch_context`).
- **G8.3 — landed**: `report pdf` (new in Go; renders
  `internal/publish/snapshot` as one A4 page).
- **G8.7 — landed**: `sync issues` (ingest; new in Go — Python has no issues
  verb at all) and `export multica` (the write half: the DAG *out* as Multica
  issues). A separate verb from `sync` on purpose — `sync` promises never to
  write to the tracker it reads, and `export` is the direction that does.
  Verified against a fake `multica` only; the first real export into a
  Multica workspace is the operator's.
- **G8.1 — landed**: `publish --to cloud` and `cloud
  setup|login|rotate|logout|status` (new in Go), against the HTTP contract in
  [`CLOUD.md`](CLOUD.md). The Worker lives in its own repository
  ([orch-cloud](https://github.com/hectorcanaimero/orch-cloud)), deployed by
  each operator to their own Cloudflare account; `cloud setup` deploys the copy
  built into the binary.
- **G1.6 / G2+ — not yet in this table**: `stop`, and everything else in
  Python's `_SUBCOMMANDS`. Add a row here in the same PR that lands one.

on success orch commits, pushes, and — when `vcs.auto_pr` is on — opens a PR from that branch into `dispatch.base_branch`, records the URL, and leaves the task `in-progress` for the CI poller to finish (green → done, and merged when `github.auto_merge` is on, with `gh pr merge --squash --auto` as Python did; and the database learns a task is `in-progress` at dispatch and `done` when CI passes, which Python does via `scripts/task-start.sh` and its queue's own mirror. **A run waits on its own PRs' CI** (Go only, #239): with nothing running and nothing ready, `orch run` stays up while a task of this run has a PR with CI pending, logging `waiting on CI`, so the poller finishes it and its dependents dispatch in the same run. Python exited there and left the green CI for the next `orch run`. Ctrl-C still drains and exits. **New task branches start from `origin/<base_branch>`**, fetched just before (#236), so a task dispatched right after its dependency merged has that merge; with `--no-push` or a failed fetch, the local base is used. **CI polling did not work at all until this was fixed**: both binaries ran `gh pr checks --json state,conclusion`, and `gh` has no `conclusion` field — the command failed and the failure was swallowed into "pending", so a green CI was never noticed, `ci_max_retries` never tripped and `auto_merge` never fired. Go now asks for `name,state,bucket`, matches gh's UPPERCASE `state` case-insensitively, and reports a failed `gh` instead of reporting "pending". The Python side is annotated, not fixed (`docs/brainstorm/go-migration-notes/opus-2.md`). **Since G6.7 a finished run writes one `sprint_done` event** (F4.7): run-level, so its `task_id` is empty, with `total`/`done`/`blocked`/`todo`/`backlog`/`in_progress`/`dispatched`/`mode` in `extra`. Emitted once, only on the exit that means the queue emptied — not after a signal (which drains and exits 130) and not when a task can never be dispatched (which is an error). "The queue emptied" is not "everything is done": a run whose remaining work is all blocked ends there too, and `blocked > 0` is what says so. `sprint_done` is **Go only** — Python declares no such event type, which is safe in a shared `orch.db` because Python validates a type on write and never filters on it when reading (see `goOnlyEventTypes` in `internal/state/eventtypes_test.go`). **`orch events` cannot show it**: that command takes a required `TASK_ID` (Python's does too) and this row belongs to no task. It is visible in the dashboard's `/api/events` and its live stream, and through the MCP `orch_events` tool with no `task_id`. Relaxing `orch events` to an optional positional would fix that and is a CLI-surface change worth deciding on its own. **Since G6.6 the dispatch prompt offers the MCP tools first** and `scripts/task-{finish,block}.sh` as the fallback, and its "Completed dependencies (context)" block finally carries what each dependency reported — read from `tasks_runtime` at dispatch time, not from tasks.json (bug 24). See [`MCP.md`](MCP.md) and `internal/prompt/testdata/README.md`. |

## Conventions every row above follows

- **Project flags** (`--project-root`, `--project-id`, `--config`) are
  persistent flags on the root command (`internal/cli/root.go`), not
  repeated per subcommand in the Go source — but they work identically to
  Python's per-subcommand `_add_common_project_flags`.
- **Exit codes**: `0` success, `1` config/project-layout error (except
  `reset`/`validate`, which use `2` for that check, matching Python) —
  beyond that, codes are per-command and match Python's own table: `2` for
  "not found" (`logs`'s missing log file, `task-status`'s unknown task id or
  invalid status) **or** "validation found a problem" (`validate`, where `2`
  means at least one error-severity finding — a different thing from the
  layout-error `2` above, both matching Python's own overload of the same
  code), `3` for an illegal status transition (`task-status`, `task set`).
  `errNotImplemented`/`exitError` in `root.go` is the shared mechanism any
  command uses to pick a non-1 code; `withSilentExitCode` (also `root.go`)
  is the variant for a non-zero exit that isn't itself an error to report on
  stderr — `validate`'s own report, already on stdout, is the explanation.
- **`--json` output** is compact (`encoding/json`'s default, HTML-escaping
  off) — same byte shape category as Python's
  `json.dumps(..., separators=(",", ":"))`, verified command-by-command by
  `scripts/parity.sh` while both binaries lived on `main` (until G7.5), and
  held since by the frozen goldens under `testdata/parity-project/`.
| `init` | `PATH` (positional, optional), `--template NAME`, `--project-name`, `--force`, `--sdd` | no — scaffolds files and prints a banner | Ports `init_cmd.py`'s `run_init_cli`, batch and interactive. Mode is chosen Python's way: a path or any of the four flags means batch, none means the wizard. **Two fixes are baked in rather than ported.** (1) A templated project's own task models are routed during init, so the first command the banner suggests works — Python's stub was empty and every templated project failed `--dry-run` until #141 (bug 14).
