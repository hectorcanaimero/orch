# `orch` (Go) — implemented subcommands

A short, living page: what the Go binary actually does today, updated in the
same PR that wires a new subcommand. The trilingual manual
(`docs/MANUAL.{en,es,pt}.md`) describes the **Python** `orch` and stays valid
as the flag *contract* — a subcommand listed here should accept the same
flags Python does unless a difference is called out.

**Status by phase** (see the "Orch en Go" migration plan):

- **G1.5 — landed**: `status`, `tasks`, `events`, `logs`.
- **G4.4 — landed**: `init` (batch + wizard).
- **G3.6 — landed**: `task set`, `task-status`, `reset`. `stop` was split out
  to **G3.3** (it needs the engine's run tracking, not `Backend.Transition`
  — see `docs/brainstorm/go-migration-notes.md`).
- **G1.6 — landed**: `validate`, `graph`, `router validate`, `router
  add-missing`, `config show`, `atomize`.
- **G4.6 — landed**: `migrate` (narrower than Python — see its table row).
- **G8.5 — landed**: `dashboard --portfolio` (new in Go — one process, N
  projects; see [`DASHBOARD-PROFILES.md`](DASHBOARD-PROFILES.md)).
- **G6.7 — landed**: `notify test`, `notify digest`. The `sprint_done` event
  (F4.7) lands with them: `orch run` writes one run-level row when its queue
  empties, carrying the task counts it finished with — see the `run` row.
- **G6.4 — landed**: `mcp` (new in Go — Python has no MCP server; see
  [`MCP.md`](MCP.md)). **G6.6** then made `run`'s dispatch prompt offer those
  tools first, with the scripts as the fallback.
- **G6.5 — landed**: `install-skills` (wider than Python — see its table
  row). Six skills are embedded: `orch`, the operating manual, and the
  planning pipeline `orch-plan` → `orch-prd` → `orch-arch` → `orch-spec` →
  `orch-tasks` (idea → `docs/prd/` → `docs/arch/` → `specs/` →
  `orch atomize --apply`). The five pipeline skills were written for G6.5 —
  before it they existed only as names in the docs. Each one is checked
  against this binary in `internal/cli/skills_contract_test.go`: every
  `orch …` invocation must resolve to a real command and flag, and
  `orch-spec`'s example spec must go through the real atomize parser with no
  warnings. Two came later: `orch-tdd`, how an agent works a task
  test-first (see `dispatch.tdd` in [`CONFIG.md`](CONFIG.md)), and `orch-e2e`,
  how an agent explores a running app in a browser and leaves Playwright specs
  (the E2E task `orch-spec` ends a phase with screens with).
- **G4.5 — landed**: `doctor` (narrower than Python — see its table row).
  `internal/doctor`'s checks (the package) landed earlier; this is the
  `orch doctor` command surface on top of them, wired separately.
- **G5.2 / G5.4 / G5.6 — landed**: `dashboard` (the HTTP server, the nine read
  endpoints the SPA consumes, the two tunnel routes and the live event stream).
- **G6.8 — landed**: `explain` (new in Go; shares `internal/explain.Gather`
  with the MCP server's `orch_context`).
- **G8.3 — landed**: `report pdf` (new in Go; renders
  `internal/publish/snapshot` as one A4 page).
- **G8.7 — landed**: `sync issues` (ingest; new in Go — Python has no issues
  verb at all) and `export multica` (the write half: the DAG *out* as Multica
  issues). A separate verb from `sync` on purpose — `sync` promises never to
  write to the tracker it reads, and `export` is the direction that does.
  Verified against a fake `multica` only; the first real export into a
  Multica workspace is the operator's.
- **export clickup — landed**: the DAG mirrored into a ClickUp Folder through
  ClickUp's REST API (a personal token, not the ClickUp MCP, which is capped at
  100 calls a day). Unlike `export multica` it is re-runnable as a mirror:
  statuses, custom fields and dependencies follow orch on every run. Verified
  against an in-memory fake (`internal/export/clickuptest`).
- **G8.1 — landed**: `publish --to cloud` and `cloud
  setup|login|rotate|logout|status` (new in Go), against the HTTP contract in
  [`CLOUD.md`](CLOUD.md). The Worker lives in its own repository
  ([orch-cloud](https://github.com/hectorcanaimero/orch-cloud)), deployed by
  each operator to their own Cloudflare account; `cloud setup` deploys the copy
  built into the binary.
- **G1.6 / G2+ — not yet in this table**: `stop`, and everything else in
  Python's `_SUBCOMMANDS`. Add a row here in the same PR that lands one.

#363), agent permissions (**one `<cli>.permissions` check per CLI the project uses** — its tasks' models plus the `meta.default_<tier>_model` keys — and none for the others, #400/#392: `claude.permissions` is a **warning** when the project's settings do not allow `mcp__orch`, `Bash(scripts/task-finish.sh:*)` and `Bash(scripts/task-block.sh:*)` — claude refuses its agents orch's tools without them, remediation `orch claude-permissions`, #361; `agy.permissions` the same for agy's two `command(...)` rules, remediation `orch agy-permissions`, #383; `codex.permissions` is ok when `codex exec --help` lists `--add-dir`, which orch passes on every dispatch to grant the sandbox the state directory, and a **warning** when this codex lacks it, #387; `opencode.permissions` and `muse.permissions` are ok — orch runs them with `--auto` and `--approval-mode never --disable-sandbox`; `gemini.permissions` is skipped as **unknown**: orch has not verified whether headless `gemini -p` lets the agent run `scripts/task-finish.sh`), onboarding progress (`onboarding.progress`, always ok: `init ✓ (blank) → first dispatch ✓ (claude) → first finished task ·` and, until the last step, the next command — read from the project's own events and `.orchestrator/state/onboarding.json`, telemetry on or off, #378), compose isolation (`compose.isolation`: a **warning** when a `docker-compose*.yml`/`compose*.yml` at the root or one directory down sets a fixed top-level `name:` or publishes a fixed host port, which collide when tasks run in parallel worktrees; keys checked: `dispatch.worktree_setup`, and with `verify.enabled` `verify.commands`, `verify.app.start`/`stop`, `verify.e2e`; shell builtins, leading `VAR=value` and words the shell expands pass; `orch run` prints the same as a warning before the first dispatch and runs anyway, and the dashboard's Tools page shows it, #440), and SQLite health. Same `{project, backend, checks, summary, exit_code}` envelope as `build_doctor_report`'s JSON (`Check`'s own json tags already match `CheckResult.as_json()`), same exit-code convention as `validate` (0 clean, 1 warnings only, 2 any error). **Not ported**, no Go home for these yet: `preflight.check_config_files` (config/router/budgets/tasks parse checks — `orch validate` already covers the tasks/router/config load failures a fresh project would hit) and `preflight.check_scripts` (the `scripts/task-*.sh` + `jq` check). A config or router load failure here becomes its own `config.parse`/`router.parse` error check rather than aborting before any check runs — tolerant like `validate`, since a broken project is exactly what this command exists to diagnose. **`models.defaults_installed` (#376)**: tasks.json's `meta.default_<tier>_model` keys (stamped by `orch init`) whose backend — the project router's, else orch's packaged route, else the key's prefix — is not on PATH are a **warning**, with no tasks needed: a fresh project used to report all ok while two tiers defaulted to an uninstalled agy; skipped when the meta names none. **`models.available` (#397)**: asks each CLI on PATH that the router uses and that can list its models (`opencode models`, `agy models`, `codex debug models`; 5 s each, nothing spent) and **warns** about routes whose `cli_model` it does not list; a hint, since an account may not reach a listed model — skipped when no such CLI is installed or every list failed. **Readiness report (#392)**: `tasks.parse` (an **error** when tasks.json does not load — it used to read as zero tasks) and `tasks.valid` (`graph.Validate`'s first error: schema, dependencies, cycles) join the config checks; `tasks.ready` says what `orch run` would dispatch now (`graph.Ready`, with the database's status via `project.Hydrate`, tasks.json's when there is no database yet) — a **warning** when nothing is ready and nothing is in progress or the file has no tasks; `tasks.backlog` lists the backlog tasks whose dependencies are done with `orch task-status <id> todo` for each (a **warning** when nothing is ready, ok otherwise, skipped when none). The human report prints the checks in five sections — Config, Backends (`models.available` included: what a CLI serves), Tasks, Permissions, Environment — and ends on a verdict: ``Ready to `orch run`.`` or ``Not ready to `orch run`: <check> — <detail>`` with its remediation. The blocker is the first check, in that section order, that is an error, or a warning about tasks or permissions (an agent that cannot report done fails its attempt after the work). `--json` adds `section` to each check and `"verdict": {"ready": bool, "blocker": <check>}` to the envelope; the rest of the shape is unchanged. **Agent CLI versions (#448):** `backend.<name>.version` compares each backend's `--version` with its npm package's `latest` (claude `@anthropic-ai/claude-code`, codex `@openai/codex`, gemini `@google/gemini-cli`, opencode `opencode-ai`; read once a day per package, cached in `~/.orch/cli-versions.json`, 2 s cap): `warn` "claude 2.1.290 → 2.1.301 available: `npm install -g @anthropic-ai/claude-code@latest`" with the command for how the binary was installed (a path in a `node_modules` → npm, under Homebrew → `brew upgrade`, claude's or opencode's own installer → `claude update` / `opencode upgrade`, unrecognized → every one), `ok` when current, `skip` when the latest is unknown (agy and muse have no feed, the registry is unreachable) or the check is off (`update.check_clis: false`, `ORCH_NO_UPDATE_CHECK`). Never an error; orch never updates a CLI. |

| `task add` | `--id`, `--title`, `--model` (all required), `--description`, `--reason`, `--spec-ref`, `--deps a,b`, `--files a,b`, `--phase N`, `--estimate H`, `--backlog`, `--project-root`, `--project-id`, `--config` | no | **New in Go (v0.22).** Adds a task to `tasks.json`: `todo` (or `backlog` with `--backlog`), seeded in the database at once. **The task editor** behind it, `task edit` and `task set --model` is the one path the dashboard uses too: it takes a lock under the state directory (`tasks.lock`) so two edits never write over each other, reads `tasks.json`, applies the change, refuses an edit that adds a validation error — a duplicate id, a missing dependency, a cycle, a model with no route — while one the project already had does not block it, writes the file atomically (a temp file and a rename; no `.bak`, since `tasks.json` is versioned with git), upserts the definitions in the database and records a Go-only `task_added` / `task_edited` event (`source`, and the `fields` an edit changed). Keys orch does not know survive the rewrite. A refused edit exits 1. **The dashboard** (v0.22) writes through the same editor: `POST /api/tasks` (body: `id`, `backlog`, and the fields `PATCH` takes; 201) and `PATCH /api/task/{id}` (any of `title`, `description`, `model`, `reason`, `spec_ref`, `phase`, `estimate_hours`, `dependencies`, `files`; 400 when it has none), recorded with `source: dashboard`; a refused edit is 422 with its reason, an unknown task 404. | `task stop` | `--id` (required), `--hold`, `--note TEXT`, `--project-root`, `--project-id`, `--config` | no | **New in Go (#356).** Ends a running task's attempt. With an `orch run` on the project (its run lock is held, or — under `--task-locks` — the task's dispatch process is alive) it writes an `operator_stop` request event (`extra`: `hold`, `requested_by`); the run reads requests every tick, SIGTERMs that task's process group (SIGKILL 10 s later), and finishes the attempt as **cancelled**: no failure class, no retry decision, its outcome event is `operator_stop` with `stopped: "attempt"` instead of `fail`. `--hold` then blocks the task with the note `held by the operator` (unblock with `orch task set --status todo`); without it the task is dispatched again at once **as the same attempt number**, so the operator's stop does not count against `retry.max_attempts`. `--note` is added first (as `task note`), so the next attempt's prompt carries it. A task not running when the run reads the request is held (`--hold`), dispatched now when it was waiting out a retry's backoff, or left alone; a task that already reported done keeps its work. The command waits up to 15 s for the run's answer and prints it: `stop requested: the running orch run ends F1.T2's attempt and holds it (blocked, "held by the operator")` then `stopped: F1.T2's attempt ended; the task is held (blocked) — `orch task set --id F1.T2 --status todo` releases it`. **With no run** it is a plain status change and says so: `no orch run is running: F1.T2 in-progress -> todo` (`--hold`: `-> blocked`); `nothing to stop` for a task that is not in progress. Exit 1 unknown task, 3 illegal transition (`--hold` on a done task). The same request as MCP `orch_task_stop` and the dashboard's `POST /api/task/{id}/stop` (body `{hold, note}`), which answer without waiting. Both endpoints answer only the operator profile, from this machine (loopback peer and Host, no relay headers) and from the dashboard's own origin — 403 otherwise, so a tunnel cannot reach them; they are the one write the dashboard makes, and it writes requests `orch run` acts on. The task's page (`/work/tasks/<id>`, #374) has the note box and, while the task runs, **Stop and redirect** / **Stop and hold**. |
| `task salvage` | `--id` (required), `--accept BRANCH`, `--project-root`, `--project-id`, `--config` | no | **New in Go (#391).** The work an earlier attempt committed and never published: `orch/<id>` and the `orch/<id>-salvage-<time>` branches, each with the commits `origin/<dispatch.base_branch>` (else the local base) lacks, as `git log --oneline`, then the command that accepts one. **Salvage branches** are what a new attempt's worktree leaves instead of deleting `orch/<id>`: when that branch holds commits neither the base nor any remote has — a task that ended blocked before a push — `git branch -D` would have destroyed the only copy, so it is renamed and a WARN names it; pushed work is cleared as before. `orch doctor` reports them (`worktree.orphans`) instead of listing them for deletion. `--accept BRANCH` takes that branch as the task's result without running its agent again: it becomes `orch/<id>` (refused when `orch/<id>` already exists with other work), so a dependent's worktree merges it like any finished task's branch, the task moves to `done` (through `todo` when needed) with a note, a Go-only `salvage_accepted` event records the branch and commit count, and it prints the `git push` and `gh pr create` that publish it. A branch with nothing the base lacks is refused (exit 1). |

## Conventions every row above follows

- **Project flags** (`--project-root`, `--project-id`, `--config`) are
  persistent flags on the root command (`internal/cli/root.go`), not
  repeated per subcommand in the Go source — but they work identically to
  Python's per-subcommand `_add_common_project_flags`.
- **Exit codes**: `0` success, `1` config/project-layout error (except
  `reset`/`validate`, which use `2` for that check, matching Python) —
  beyond that, codes are per-command and match Python's own table: `2` for
  "not found" (`logs`'s missing log file, `task-status`'s unknown task id or
  invalid status) **or** "validation found a problem" (`validate`, where `2`
  means at least one error-severity finding — a different thing from the
  layout-error `2` above, both matching Python's own overload of the same
  code), `3` for an illegal status transition (`task-status`, `task set`).
  `errNotImplemented`/`exitError` in `root.go` is the shared mechanism any
  command uses to pick a non-1 code; `withSilentExitCode` (also `root.go`)
  is the variant for a non-zero exit that isn't itself an error to report on
  stderr — `validate`'s own report, already on stdout, is the explanation.
- **`--json` output** is compact (`encoding/json`'s default, HTML-escaping
  off) — same byte shape category as Python's
  `json.dumps(..., separators=(",", ":"))`, verified command-by-command by
  `scripts/parity.sh` while both binaries lived on `main` (until G7.5), and
  held since by the frozen goldens under `testdata/parity-project/`.
