# `orch` (Go) — implemented subcommands

A short, living page: what the Go binary actually does today, updated in the
same PR that wires a new subcommand. The trilingual manual
(`docs/MANUAL.{en,es,pt}.md`) describes the **Python** `orch` and stays valid
as the flag *contract* — a subcommand listed here should accept the same
flags Python does unless a difference is called out.

**Status by phase** (see the "Orch en Go" migration plan):

- **G1.5 — landed**: `status`, `tasks`, `events`, `logs`.
- **G4.4 — landed**: `init` (batch + wizard).
- **G3.6 — landed**: `task set`, `task-status`, `reset`. `stop` was split out
  to **G3.3** (it needs the engine's run tracking, not `Backend.Transition`
  — see `docs/brainstorm/go-migration-notes.md`).
- **G1.6 — landed**: `validate`, `graph`, `router validate`, `router
  add-missing`, `config show`, `atomize`.
- **G4.6 — landed**: `migrate` (narrower than Python — see its table row).
- **G6.4 — landed**: `mcp` (new in Go — Python has no MCP server; see
  [`MCP.md`](MCP.md)).
- **G6.5 — landed**: `install-skills` (wider than Python — see its table
  row). Only the `orch` skill is embedded in this repo today; the five
  pipeline skills this project's own `CLAUDE.md` lists as relevant
  (`orch-plan`/`orch-prd`/`orch-arch`/`orch-spec`/`orch-tasks`) live on the
  operator's machine, not in this repo, and have no checked-in home yet —
  `--all` installs whatever *is* embedded, so adding one later is a new
  `internal/skills/<name>/SKILL.md` directory and nothing else.
- **G4.5 — landed**: `doctor` (narrower than Python — see its table row).
  `internal/doctor`'s checks (the package) landed earlier; this is the
  `orch doctor` command surface on top of them, wired separately.
- **G5.2 — landed**: `dashboard` (the HTTP server + the nine read endpoints
  the SPA consumes; the tunnel routes and the SSE stream are G5.6/G5.4).
- **G1.6 / G2+ — not yet in this table**: `stop`, and everything else in
  Python's `_SUBCOMMANDS`. Add a row here in the same PR that lands one.

SIGINT and SIGTERM both drain in-flight work and exit **130**; a second signal SIGKILLs every child process group. **Worktree mode, auto-PR and CI polling are wired** (`--worktree-mode`, or `dispatch.worktree_mode`): each task gets its own git worktree and branch and the agent runs inside it; on success orch commits, pushes, and — when `vcs.auto_pr` is on — opens a PR from that branch into `dispatch.base_branch`, records the URL, and leaves the task `in-progress` for the CI poller to finish (green → done, and merged when `github.auto_merge` is on; and the database learns a task is `in-progress` at dispatch and `done` when CI passes, which Python does via `scripts/task-start.sh` and its queue's own mirror. **Known gap, same as Python**: a run that opens a PR exits before CI is polled, so a green CI is noticed on the *next* `orch run` — one poll per invocation. |

## Conventions every row above follows

- **Project flags** (`--project-root`, `--project-id`, `--config`) are
  persistent flags on the root command (`internal/cli/root.go`), not
  repeated per subcommand in the Go source — but they work identically to
  Python's per-subcommand `_add_common_project_flags`.
- **Exit codes**: `0` success, `1` config/project-layout error (except
  `reset`/`validate`, which use `2` for that check, matching Python) —
  beyond that, codes are per-command and match Python's own table: `2` for
  "not found" (`logs`'s missing log file, `task-status`'s unknown task id or
  invalid status) **or** "validation found a problem" (`validate`, where `2`
  means at least one error-severity finding — a different thing from the
  layout-error `2` above, both matching Python's own overload of the same
  code), `3` for an illegal status transition (`task-status`, `task set`).
  `errNotImplemented`/`exitError` in `root.go` is the shared mechanism any
  command uses to pick a non-1 code; `withSilentExitCode` (also `root.go`)
  is the variant for a non-zero exit that isn't itself an error to report on
  stderr — `validate`'s own report, already on stdout, is the explanation.
- **`--json` output** is compact (`encoding/json`'s default, HTML-escaping
  off) — same byte shape category as Python's
  `json.dumps(..., separators=(",", ":"))`, verified command-by-command in
  `scripts/parity.sh` rather than assumed.
| `init` | `PATH` (positional, optional), `--template NAME`, `--project-name`, `--force`, `--sdd` | no — scaffolds files and prints a banner | Ports `init_cmd.py`'s `run_init_cli`, batch and interactive. Mode is chosen Python's way: a path or any of the four flags means batch, none means the wizard. **Two fixes are baked in rather than ported.** (1) A templated project's own task models are routed during init, so the first command the banner suggests works — Python's stub was empty and every templated project failed `--dry-run` until #141 (bug 14). (2) The router stub is comments only, never `{}`, so `router add-missing` can append to it (#141 Python side, #144 Go side). **Divergences, all approved:** the wizard's choice hint is inlined only when every choice is slash-free and there are at most six — Python's unconditional `'/'.join` made the model tier picker unreadable, since the router keys *are* slash-separated (`orch init` is interactive and not diffed by `scripts/parity.sh`); running out of input is an error rather than an implicit yes, because the confirm gate's default is `y` and a closed pipe must not scaffold a project nobody approved; and a config key the template omits is appended rather than silently dropped — no shipped template contains `budgets_preset`, so Python asks for one, shows it in the confirm summary, and discards it (bug 17). The fifth template, `expo-mobile`, exists only in Go (H-1e). Batch mode's own output (blank project, no wizard) *is* diffed — `scripts/parity.sh` (G3.5) scaffolds one with each binary and compares the resulting tree. See `docs/brainstorm/go-migration-notes/opus.md`. **Since G6.4 it also writes `.mcp.json`** (the block in [`MCP.md`](MCP.md)), a file Python's `run_init_cli` never wrote — soft even under `--force`, because a project's `.mcp.json` lists its other MCP servers too. `scripts/parity.sh` diffs the scaffolded tree, so this file is a known, intended difference there. |
| `mcp` | `--project-root`, `--project-id`, `--config` | n/a — speaks JSON-RPC on stdin/stdout, so **nothing else may be written to stdout** | **New in Go, no Python source.** A stdio MCP server over the official Go SDK (`github.com/modelcontextprotocol/go-sdk`), sharing one `state.Backend` with the engine. Seven tools: `orch_list_tasks`, `orch_get_task`, `orch_set_status`, `orch_block`, `orch_budget`, `orch_events`, `orch_context`. The two that write keep the shape `scripts/task-{start,finish,block}.sh` already have (`orch_set_status` covers start and finish; `orch_block` is the intent-carrying form), so G6.6 can offer MCP first and fall back to the scripts without either side learning a new vocabulary. An illegal transition is a **tool** error, not a protocol error: the payload names the task's current status and every status it may legally move to, because the caller is a model that can retry. `.mcp.json` is written by `orch init` from this PR on — never overwritten, `--force` included, since it is shared with a project's other MCP servers. Bootstraps the project at startup, and again on a write to a task tasks.json has and the database does not, so a long-lived server does not go stale the way a per-invocation `orch task-status` cannot. Exit 0 when the client disconnects, 1 on a project-layout or database error. See [`MCP.md`](MCP.md). |
| `dashboard` | `--host` (default `127.0.0.1`), `--port` (default `7420`, `0` = any free one), `--profile {operator,stakeholder,both}`, `--token`, `--tunnel`, `--project-root`, `--project-id`, `--config` | no — it serves until Ctrl+C | Ports the `run` function in `orchestrator/dashboard/server.py`, minus uvicorn: the server is `net/http` and the SPA is embedded in the binary, so there is nothing to install and nothing to serve from disk. Flags win over `dashboard:` in config.yaml, and only when passed — an unset flag never overwrites a configured value with its zero. **Read-only by construction**: the server takes a narrow `StateReader`, not the `Backend`, so a second writer to a single-writer database is not something a future handler can add by accident. **Three refusals at startup rather than at request time**: an unknown profile (a typo in a flag meant to RESTRICT access would otherwise ALLOW everything — `decide` reads an unrecognised profile as "no stakeholder context"), a stakeholder profile with no token (every request 401s, including the SPA's own token form), and a port outside 1-65535. **Two differences from Python, both deliberate**: the banner prints AFTER the listener is open, so the URL in it already answers — Python prints before uvicorn binds — and the LAN line reads the interfaces instead of resolving the hostname, which on any Debian whose hostname maps to `127.0.1.1` prints a loopback address labelled LAN. `--reload` is not ported: it is uvicorn's, and a binary with the SPA embedded has nothing to reload. Endpoints: the nine the SPA consumes (G5.2 b1-b3), `/api/whoami`, `/api/config/status`, and the two tunnel routes (`/api/tunnel/capabilities`, `/api/tunnel/status`); the SSE stream is G5.4. **`--tunnel` starts the configured tunnel and stops it on exit** — Python drives start/stop from the SPA as POST routes, which G5.5's read-only trim left without a consumer, so the lever moved to the command line where the person holding it is the person who started the process. It refuses without `tunnel.enabled: true`, and refuses under any profile but `operator`: raising a public URL from a dashboard whose own gate says the operator is absent is not a thing to do quietly. **`/start`, `/stop` and `/logs` are not ported** — no consumer, and this server takes a read-only `StateReader` by construction (rule 13). The tunnel gates run in a fixed order (config → operator profile → loopback host) and PATH is consulted only after all three pass, so a caller who may not ask never learns what the box has installed. |
